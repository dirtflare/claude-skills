# SNS 投稿解析スキル(X / Instagram / TikTok / Shorts)

SNS の投稿を「取得 → 抽出 → 検証 → 構造化」する運用手順。
スキルは取得エンジンではなく指示書である:
取得手段(Web取得・API・ブラウザ・画像理解)を状況に応じて切り替え、
LLM が意味を解析し、定めた形式で出力する。

**このスキルは特定のアプリやリポジトリに紐付かない。**
解析結果をどこかに保存・反映するのは、ユーザーが明示的に
出力先(設計書、ワークフロー、メモ、コード等)を指定した場合だけ。
指定が無ければチャットでの報告が成果物である。

## Step 1 — プラットフォームと URL の種類を判定

| URL | 判定 |
|---|---|
| `x.com` / `twitter.com` の `/status/<id>` | X の投稿本体 |
| `instagram.com/reel/<id>/` `/p/<id>/` | Instagram の投稿本体(両者は等価) |
| `tiktok.com/@<user>/video/<id>` | TikTok の投稿本体 |
| `youtube.com/shorts/<id>` | Shorts の投稿本体 |
| プロフィール URL | 投稿が特定できない。**どの投稿かを確認する**(特に TikTok はプロフィールから動画 ID が取れない) |
| 短縮 URL (`t.co` / `vm.tiktok.com` 等) | 展開してから再判定 |

トラッキングパラメータ(`?igsh=` `?is_from_webapp=` 等)は落とす。

## Step 2 — 取得する

**プラットフォームごとの具体的な手段・コマンド・効かない手段は
[references/retrieval.md](references/retrieval.md) に記載。必ず参照する。**

要点だけ:

- **リモート実行環境ではブラウザ操作(Playwright)は現状ほぼ使えない**
  (プロキシ CA の問題。TLS 検証を切って回避してはいけない)。
  主経路は **curl + メタタグ / oEmbed**
- Instagram → 投稿ページの **OG メタタグ**(キャプション全文・いいね数・
  コメント数・投稿日・@ハンドル・カバー画像が揃う)。
  **User-Agent はクローラ系(`Mozilla/5.0 (compatible; bot)`)を使う。**
  デスクトップ Chrome を騙ると OG タグが入らない空シェルが返る
- TikTok → **oEmbed**(キャプション全文・投稿者・音源名・カバー画像)
- X → WebFetch → `api.fxtwitter.com` ミラー
- **カバーフレーム(サムネイル)は必ず1枚落として画像として読む。**
  釣り文句や結論がサムネ文字として焼き込まれていることが多く、
  キャプションだけでは分からない主張が読み取れる
- 全滅したら、失敗理由を一言で伝えて**素材を1つだけ**依頼する

**動画本体はどのプラットフォームでも取得できない。**
音声・全フレームに依存する内容は、字幕・文字起こし・要約を
もらうか、**「動画未視聴」として明記する。**

## Step 3 — 抽出

取得したものが HTML でも JSON でも、乱雑なコピペでも、
スクリーンショットでも、同じものを抽出する:

- **投稿者**: 表示名、@ハンドル、認証マーク、アカウントの性格
  (新規/量産/AI 生成アバターの兆候など、判断に効くもの)
- **本文 / キャプション**: X のスレッドは順序を復元。引用・返信は本体と区別
- **日時・エンゲージメント**(読み取れれば)。
  **投稿直後か、数字が伸びているかは検証の材料になる**
- **カバーフレーム**: 焼き込み文字、話者、画面録画に映っている UI・
  リポジトリ名・コマンド
- **画像**: 図、ストーリーボード、プロンプト例、複数画像の順序と関係
- **動画**: 本文・カバー・字幕・提供された要約から分かる範囲を再構成。
  **見ていない場合はその旨を必ず明記**
- **音源名**(TikTok/リール): トレンド音源かオリジナルか
- **ハッシュタグ**: 数と内容。**大量の汎用タグは内容の薄さの指標**
- **外部リンク**: 展開して中身も確認する価値があるか判定

UI ノイズ(いいね/リポスト等のラベル、カウント、「さらに表示」、
プロモーション表示)は除去する。迷ったら削らず「要確認」として残す。

## Step 4 — 検証(主張と事実を分ける)

1. 投稿者の**主張**と**確認可能な事実**を分離する
2. 製品仕様・API・リリース・統計は**公式情報**(公式ドキュメント、
   GitHub、一次ソース)で照合する。SNS 自体は検索でも読めないことが
   多いので、一次ソースを直接当たる
3. **ツールを紹介する投稿では、名指しされた実体まで到達する。**
   リポジトリ名が出ていれば ★数・最終更新・コミット数・ライセンス・
   依存ライブラリ・README の免責事項まで確認する。
   名前が出ていない場合は**それ自体を所見として書く**(下記)
4. 時点依存の情報(料金、機能、制限)は取得日を添える
5. 確認できないものは推測で埋めず「**確認不能**」として残す

### エンゲージメント・ベイトの判定

短尺動画では特に頻出する。次の兆候があれば**明示的に指摘する**:

- **「◯◯とコメントしたらリンクを送る」** — ツール名を書けば済むところを
  伏せている。情報提供ではなく DM リスト収集が目的
- ツール名・リポジトリ名が本文にもカバーにも一切無い
- 投稿直後で反応が極小(内容が検証された形跡が無い)
- 汎用ハッシュタグの大量列挙
- アフィリエイト・有料ニュースレター・情報商材への誘導
- 「無料」「数分で」「誰でも」等の断定的な誇張

これらは**内容の真偽とは別軸**として扱う。主張自体は本当でも、
投稿から得られる情報量がゼロなら「追う価値なし」と結論して良い。

### 安全性・法務の観点

内容が次に触れる場合は、採否の判断材料として一言添える:

- 他者の著作物・デザイン・アセットの複製や流用
- スクレイピング対象の利用規約 / robots.txt
- red-team / phishing 用途を作者自身が明示しているツール
- 認証情報・個人データを扱うもの

## Step 5 — 構造化して出力

既定の報告形式:

```
## 要約
(投稿者 / 日時 / 何についての投稿か、2〜3 文)

## 内容の構造化
(手順・プロンプト・設計など、投稿が伝えている中身を再利用できる形で)

## 主張と検証結果
(✅公式情報と一致 / ⚠️確認不能 / ❌誤り、それぞれ根拠付き)

## メリット / リスク
(この内容を採用する場合の利点と注意点)

## 確認不能だった点
(取得できなかった部分、動画未視聴など。無ければ省略)
```

**「自分に有用か判断して」と聞かれた場合**は、上記に加えて
**結論を先に出す**。判断はユーザーの現状を踏まえて行う:

- 手元の環境・リポジトリで**既に実現できていないか**
  (できているなら「パワーアップしない」が結論)
- 既存のツール・スキル・MCP との重複
- 導入コストと、得られる差分

ユーザーが出力先を指定した場合(設計書にして、ワークフローに変換して、
○○リポジトリに取り込んで等)は、この構造化結果を基にその形式へ変換する。
指定が無い限り、ファイルやコードへの保存・反映は行わない。
