# リテイクの運用術

HyperFrames の真価は1本目ではなく**2本目以降、つまり修正の場面**に出る。

従来の動画外注では、一往復に数日の待ちと追加費用がかかった。
だから僕らは修正を我慢して、微妙な違和感の残った動画をそのまま世に出していた。
**その我慢が消える。** 納得いくまでノーコストで直せる環境は、
アウトプットの天井を確実に引き上げる。

---

## 基本原則: 見たままの不満を、そのまま言う

実際に通る修正指示:

- 字幕の枠を外して、色の変化だけにして
- この文字が上の行と被ってるから、下に逃して
- 締めのカードは1枚にまとめて、最後は緑のバナーで止めて
- 図解は画面の左3分の1に寄せて
- 発話中の単語はグレー、いま話している単語は青にして
- 最初の締めカードは削って、最後はバナーで止めて

**映像の専門用語をひとつも使っていない。**
イージングがどう、キーフレームがどう、とは一切言っていない。
見たままの不満と、欲しい状態を、そのまま言葉にしているだけ。

それでもエージェントは意図を汲んで、該当シーンを直し、
レイアウトの検証をやり直し、音との同期を保ったまま再レンダリングして返す。

---

## コツ: 1回の指示に詰め込まない

**一文か二文で1テーマ、返ってきたら次。** このリズムが結局一番速い。

悪い例:

```
字幕の枠を外して、あと2シーン目の背景が暗いから明るくして、
それと締めのカードが2枚あるので1枚にまとめて、
ついでに全体を10秒短くして、ロゴも大きくして。
```

→ どれかが中途半端になる。検証も何が原因で崩れたか分からなくなる。

良い例:

```
字幕の枠を外して、色の変化だけにして。
```

→ 返ってきたら次の一文。

---

## 部分だけ直させる

「シーン2の背景だけ変えて」と言えば、
**承認済みの他のシーンには手を触れずに**シーン2だけ作り直す。
全体を作り直させる必要はない。

すでに OK が出ているシーンを明示的に守らせたいときは一言添える:

```
シーン2の背景だけ変えてください。他のシーンは触らないでください。
```

---

## 直したあとに崩れていないか確認させる

修正がレイアウトや同期を壊していないかは、CLI に検証させる:

```bash
npx hyperframes check      # コンポジションの検証
npx hyperframes preview    # ブラウザで目視。保存すると即反映
```

プレビューで詰めてから最後に1回 `render` する。
これが一番速く、一番失敗しない。

---

## 何をどこまで任せるか

**9割をプロンプトで、1割を目で。** これは HeyGen 側の言い方でもある。

エージェントに任せるべきもの:

- 構成・台本・尺の配分
- 色とフォントの適用 (`frame.md` がある前提)
- 動きのデザイン (エフェクト名を指定しないほうが良い結果になる)
- 音との同期
- エラーの解読と修正

人間の目でしか気づけないもの:

- 字幕が顔に被っている
- カットが半拍遅い / 早い
- 数字や固有名詞の事実誤認
- そのブランドとして「なんか違う」という違和感

---

## エラーが出たとき

**赤い文字のエラーメッセージを丸ごと貼る。** それだけ。
原因を特定して、修正して、もう一度レンダリングまで回す。

エラーを解読するのは人間の仕事ではない。
出てきた動画に感想を言うのが人間の仕事。

よくある詰まりどころの切り分けは [setup.md](setup.md) の
「トラブルシュート」に集約してある。

---

## これは腐らないスキルになる

「言葉で映像を直す力」は、そのまま**ディレクション能力**として蓄積される。
編集ソフトの操作スキルと違って、ツールが変わっても腐らない。

これからの動画制作で価値を持つのは手先の器用さではなく、
**違和感を言語化する目。**
文章を書いてきた人は、実はここでかなり有利に戦える。
